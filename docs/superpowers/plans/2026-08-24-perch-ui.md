# Perch UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A spectator can choose whose eyes they are looking through, from the shipped web client.

**Architecture:** The server side is built, tested and keystoned. `SetViewpoint` exists on the wire, `MayPerch` enforces the rule, the projection re-perches correctly. What is missing is one control and one command builder. `viewpoint` currently appears exactly once in `client/src` — in a comment.

**Tech Stack:** TypeScript, `client/src/commands.ts`, `client/src/view/spectator.ts`, `client/src/app.ts`.

## Global Constraints

- **Only a spectator may perch.** `MayPerch` (`internal/gateway/viewpoint.go`) refuses every other role outright: *"role %q does not perch — a viewpoint is the spectator's"*. The control must not appear for a player, DM or agent.
- **Only a party member is perchable.** `isPartyMember` — after visibility spec §5.1, kind `PARTY_MEMBER`, not "has a controller".
- **The empty actor id is a real state, not a null.** It is how a bird leaves a shoulder without taking another, and it is where every spectator starts a connection. Offer it.
- happy-dom has no canvas, so board pixels cannot be asserted — but **this control is DOM, so it is fully assertable.** No excuse for a thin test.
- ADR-009 airtight TDD; `task check` is the gateway; no game-system vocabulary.

## Task 1: A spectator picks a shoulder

**Files:**
- Modify: `client/src/commands.ts` (add `setViewpoint`), `client/src/view/spectator.ts` (the control + a perched-on indicator), `client/src/app.ts` (pass it only for the spectator role)
- Test: `client/test/spectator-view.test.ts`, `client/test/commands.test.ts`, `client/test/app.test.ts`

**Interfaces:**
- Produces: `setViewpoint(actorId: string): ClientCommand` — note the empty string is a legal, meaningful argument.
- Consumes: `st.Actors`, filtered to party members.

- [ ] **Step 1: Write the failing tests**

Four behaviours, and the third is the one most likely to be got wrong:

```ts
// 1. The control lists party members and nothing else. A spectator receives
//    party members regardless of perch (§5's exception, project.go's flat loop
//    over st.Actors), which is exactly why this list can exist at all.
// 2. Choosing one sends setViewpoint with that actor id.
// 3. "No shoulder" sends setViewpoint(""), which is a REAL state and must not
//    be collapsed to "do nothing". A spectator uses it to stop seeing.
// 4. A player, a DM and an agent get NO control at all.
```

- [ ] **Step 2: Run to verify they fail**

Verify the RED **by seeing each test name in the output**. A filter matching nothing reports success, and that trap is in this repo's ledger.

- [ ] **Step 3: Implement**

`setViewpoint` in `commands.ts` beside the other builders. The control goes in `ViewExtras` and renders only when `me.role === "spectator"` — `app.ts:280` already computes role branches; follow that shape rather than inventing a second one.

**Show where the spectator is currently sitting.** A perch with no indicator means the board changes under you with no way to know why, and hopping is the whole feature.

- [ ] **Step 4: The reconnect hazard — read `wire.ts:233-254` before writing this**

The client cannot simply call `setViewpoint` again after a reconnect. Perch frames carry **sequence 0** so an undo cannot delete them, and `session.ts`'s rollback keeps everything at or below its cursor — so perch frames **survive a rollback that drops ordinary ones**. Naively re-perching duplicates them.

*CORRECTED 2026-08-31 — the hazard is real and the reason given for sequence 0 is not.* Retraction left the platform (`2026-08-30-retraction-leaves-design.md`), so there is no undo that could have deleted a perch frame in the first place, and `d3e2f28` replaced exactly this rationale in `client/src/wire.ts` with a durable one: **a perch has no causing event, so it has no number to inherit** — see the server's `perchSequence`. Everything that follows still holds, because it follows from the 0 and not from the reason for it: 0 is below every rollback cursor, so perch frames survive a rollback that drops ordinary ones, and re-perching naively duplicates them. Sub-project 14 generalises the lesson (`2026-08-30-per-character-logs-design.md` §1): a derived, per-viewer artifact must not borrow a log identifier, and `perchSequence` is the case that got it right.

That comment states the two workable answers: re-perch only on a connection that resumed from 0 with an empty log, or drop the sequence-0 frames from the log before re-sending. **Pick one deliberately and pin it with a test that reconnects.** This is the known latent hazard in the feature and the reason it is a task rather than an afternoon.

## Out of scope

- Clicking a token to perch. Tempting, and impossible as the only mechanism: an unperched spectator sees an empty board, so there is no token to click. It could be added *on top of* the list later, never instead of it.
- Any change to `MayPerch`, the projection, or the keystone. The server is done.
